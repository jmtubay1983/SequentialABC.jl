Summary statistics

ABC compares simulations to data through a summary statistic, and everything downstream — the distance, the tolerance ladder, the ESS, the posterior — is only as informative as that summary. The framework here makes summaries named, composable and checkable:

You writeYou get
FunctionSummary(fn, :count)one value, one name
CompositeSummary([...], :abm)a flat NamedTuple with stable key order
aggregate(reps, s)replicate mean and sd per key
pca_reduce(s, X, k)a fitted projection, with explained variance
summary_keys(s)the declared key order — the layout of the distance vector

Keys are declared, not discovered: summary_keys works before any simulation runs, so a composite can be validated when it is built, a data matrix can be checked against it, and the vector a distance function compares has a documented order. Duplicate keys are an error at construction time; two parts never silently overwrite each other.

Nothing about the engines changes. A summary is still the summary field of the simulator and the shape of the observed summary — see Plugging a summary into a sampler for the exact wiring.

A composite summary for an agent-based model

The Schelling model in examples/agents_schelling.jl reduces a finished model to one number — the segregation index. A composite replaces that single number with a named set of statistics whose individual behaviour can be inspected:

using SequentialABC, Agents, Distributions, Statistics

# The summaries receive exactly what the simulator's `summary` field receives:
# a built model, after `steps` steps.
age_summary   = FunctionSummary(model -> mean(a.age for a in allagents(model)), :mean_age)
count_summary = FunctionSummary(model -> nagents(model),                      :count)
# spatial variance of the agents' x positions — a cheap clustering diagnostic
spread_summary = FunctionSummary(model -> var([a.pos[1] for a in allagents(model)]),
                                 :spatial_var)

abm = CompositeSummary([count_summary, age_summary, spread_summary], :abm)

summary_keys(abm)          # [:count, :mean_age, :spatial_var]  — fixed forever

Each part is a plain function plus a name, so anything you already compute about a model drops in. The composite is then the simulator's summary — one line, and the named values become the vector the distance sees:

simulator = AgentsSimulator(
    model_builder = (θ, rng) -> build_model(θ[1], rng),
    step!         = (model, _rng) -> step!(model, 1),
    summary       = model -> namedtuple_to_vector(compute_summary(abm, model)),
    steps         = 100,
)

compute_summary(abm, model) returns (count = …, mean_age = …, spatial_var = …); namedtuple_to_vector lays it out in summary_keys order, which is all distance and run_inference need. The observed side is built the same way, from the same summaries — never by hand:

y_obs = namedtuple_to_vector(compute_summary(abm, observed_model))

Two details worth knowing:

  • A part that returns a NamedTuple is flattened with its name prefixed, so FunctionSummary(x -> (mean = …, sd = …), :age) contributes :age_mean and :age_sd. That is how per-key diagnostics enter a composite without extra naming work.
  • compute_summary(s, output) maps one simulator output. A Vector is a legitimate single output (a time series, a field, a set of replicates) — use aggregate when you want replicate statistics instead.

Aggregating replicates

The samplers have their own replicate knob, M: each particle simulates M times and the summaries are averaged. That is the right default, but it hides the variability. aggregate is the summary-level version and reports both:

pop_summary = CompositeSummary([FunctionSummary(length, :count),
                                FunctionSummary(mean,   :mean_age),
                                FunctionSummary(var,    :spatial_var)], :population)

pop  = [1.0, 2.0, 4.0, 8.0]
reps = [pop, 2 .* pop, 3 .* pop]           # replicate outputs of one θ

aggregate(reps, pop_summary)
# (mean_count = 4.0, mean_mean_age = 7.5, mean_spatial_var ≈ 44.72,
#  sd_count = 0.0,  sd_mean_age = 3.75, sd_spatial_var ≈ 38.73)

Keys are aggregator-major — all means, then all standard deviations, in summary_keys order — so the resulting NamedTuple has a fixed, documented layout like any other summary. aggs names the aggregators and can be replaced: aggs = (mean = mean, q90 = v -> quantile(v, 0.9)).

Two honest use cases:

  • Observed data from repeated runs. s_obs = namedtuple_to_vector(aggregate(obs_runs, pop_summary)) gives the distance a target for every key, mean and sd alike.

  • Inside the sampler, when replicas are the science. Let the simulator hand the summary a vector of replicate outputs, and aggregate there — then the replicate sd takes part in the acceptance decision, not just the mean:

    simulator = ContinuousSimulator(
    model_builder = θ -> θ,
    evolve        = (θ, rng) -> [replicate(θ, rng) for _ in 1:3],
    summary       = reps -> namedtuple_to_vector(aggregate(reps, pop_summary)),
)

    M = 1 is correct here: the replicates are the simulator's own output, and the summary — not the engine — decides how to summarise them.

Compressing a high-dimensional summary

A large summary is not automatically a good one: each extra key adds noise to the distance, and correlated keys count several times over. pca_reduce fits a projection on a pilot ensemble and keeps the k directions that carry the variance. PCA needs data, so the data matrix is explicit — one row per observation, one column per key of the summary:

# The summary being reduced: one value per key of the raw output
base = CompositeSummary([FunctionSummary(raw -> raw[1], :a),
                         FunctionSummary(raw -> raw[2], :b)], :two_keys)

# Pilot ensemble on the prior predictive distribution: one simulator output per
# prior draw, one summary vector per row (fixed seed — this is a data choice)
rng   = MersenneTwister(2026)
pilot = [sim.evolve(sim.model_builder(θ), rng) for θ in prior_draws]   # ContinuousSimulator
X     = reduce(vcat, permutedims.(namedtuple_to_vector.(compute_summary.(base, pilot))))

proj = pca_reduce(base, X, 3)      # 3 components
proj.explained                     # fraction of total variance per component
summary_keys(proj)                 # [:pc1, :pc2, :pc3]

The projection is itself a summary, so it composes and plugs in like any other — the sampler never knows PCA happened:

simulator = ContinuousSimulator(model_builder = θ -> θ,
                                evolve        = evolve,
                                summary       = raw -> namedtuple_to_vector(compute_summary(proj, raw)))
s_obs     = namedtuple_to_vector(compute_summary(proj, raw_observed))

proj(X) applies the fitted map to a whole matrix at once, and proj.explained is the diagnostic to check before shrinking a summary: if the first component carries 0.99 of the variance, the other keys were mostly noise, and k = 1 says so. Eigenvector signs are arbitrary, so each component is flipped to a canonical convention (its largest-|value| entry is positive) — refitting on the same data is bit-identical, on any machine, with any BLAS.

Plugging a summary into a sampler

There is no summaries_fn keyword, and no new per-engine plumbing: summaries enter where they always have.

PieceRole
simulator.summaryraw simulator output → summary (a number, or a vector via namedtuple_to_vector)
s_obsthe observed summary, produced by the same summary functions
distancecompares the two — for named summaries, Euclidean on namedtuple_to_vector
run_inference / run_smc / run_mcmc / run_pmcunchanged; they only see the distance

So the complete wiring is three lines plus the call you already make:

base2 = CompositeSummary([FunctionSummary(raw -> raw[1], :a),
                          FunctionSummary(raw -> raw[2], :b)], :two_keys)

simulator = ContinuousSimulator(
    model_builder = θ -> θ,
    evolve        = (θ, rng) -> θ .+ 0.3 .* randn(rng, 2),
    summary       = raw -> namedtuple_to_vector(compute_summary(base2, raw)),
)

cfg = ABCSMCConfig(prior, sample_prior, identity,
                   (s, so) -> sqrt(sum(abs2, s .- so)),
                   GaussianKernel(), [1.0 0.0; 0.0 1.0], simulator)

state = run_inference(:smc, cfg, s_obs; N = 1000, T = 5, base_seed = 2026)

The summary's key order fixes the layout of both vectors, so s_obs and every simulated summary are compared element-by-element: :count against :count, :mean_age against :mean_age. Renaming a key renames the comparison — silently adding or dropping one is caught by validate_summary_keys at the first call, not by a mysteriously worse posterior.

A runnable end-to-end script — composite, replicate aggregation, PCA compression, and all three engines — lives in examples/summaries_example.jl:

julia --project=. examples/summaries_example.jl

Units, scaling and name resolution

Keys with wildly different magnitudes make a Euclidean distance a one-key distance: a count in the thousands drowns a variance in the hundredths. scale multiplies selected keys by fixed factors and validates them against the summary, so a typo cannot silently scale nothing:

scaled = scale(abm, Dict(:count => 1e-3))    # :mean_age, :spatial_var untouched

scale is a method of Distributions.scale — the scale-parameter accessor for distributions, here meaning the rescaled summary — so using SequentialABC and using Distributions (the usual pairing, since priors are distributions) resolve it without qualification.

transform — the PCA map — is deliberately not exported. In this package transform already means the prior→model-parameter map (cfg.transform, written transform(θ_raw) = … in the Quickstart); PCA's map is reached as proj(X) or SequentialABC.transform(proj, X), so it can never collide with your own transform.

Determinism

The framework contains no randomness: summaries are pure functions of one simulator output, aggregate applies whatever aggregator you passed, and PCA is a deterministic eigendecomposition with the canonical sign convention above. Two consequences:

  • The distance vector for a given output is bit-identical across runs, sessions and machines, because it is a function of a fixed key order.
  • Fitting a projection twice on the same pilot matrix gives the same components, so a saved proj and a refitted one cannot silently differ.

state.θ, state.w, state.ε and the checkpoint format are untouched by everything on this page — the engines' determinism guarantees are the ones you already rely on (see the Design Notes page).

API

SequentialABC.AbstractSummary — Type
AbstractSummary

Supertype of the named summary types: FunctionSummary, CompositeSummary, ScaledSummary and PCAProjection.

A summary declares the keys it produces (summary_keys) and turns one simulator output into a NamedTuple with exactly those keys (compute_summary). Because keys are declared rather than discovered, composites can be validated and distance vectors have a documented order.

source
SequentialABC.FunctionSummary — Type
FunctionSummary(fn::Function, name::Symbol) <: AbstractSummary

Wrap a plain function fn(sim_output) -> value as a named one-key summary: the value is reported under name. If fn returns a NamedTuple, its keys are prefixed with name when the summary is used inside a CompositeSummary — (mean = 1.0, sd = 0.5) under :age becomes :age_mean and :age_sd.

count_summary = FunctionSummary(m -> length(m.agents), :count)
compute_summary(count_summary, model)     # (count = 42,)
source
SequentialABC.CompositeSummary — Type
CompositeSummary(summaries::AbstractVector{<:AbstractSummary}, name::Symbol) <: AbstractSummary

An ordered group of summaries. Keys are the concatenation of the parts' keys, in part order, so summary_keys of a composite reads exactly like the vector the distance function will compare; nested NamedTuples are flattened with _ prefixes (flatten_namedtuple) and duplicate keys are rejected when the composite is constructed.

abm = CompositeSummary([FunctionSummary(m -> length(m.agents), :count),
                        FunctionSummary(m -> mean_age(m), :mean_age),
                        FunctionSummary(m -> spatial_var(m), :spatial_var)], :abm)
summary_keys(abm)        # [:count, :mean_age, :spatial_var]
source
SequentialABC.ScaledSummary — Type
ScaledSummary(inner::AbstractSummary, scales::Dict{Symbol,Real}, name::Symbol)
    <: AbstractSummary

A summary whose keys are multiplied by fixed factors — one per key, e.g. to put summaries with different units on a comparable scale before they share a distance function. Keys absent from scales are left unchanged; keys in scales that the inner summary does not produce throw an ArgumentError, so a typo cannot silently scale nothing. See scale.

source
SequentialABC.PCAProjection — Type
PCAProjection <: AbstractSummary

A fitted PCA map from a source summary's keys to k principal-component scores named :pc1, :pc2, …, :pcK. Built by pca_reduce; apply it to a single simulator output with compute_summary, to a whole matrix of summary vectors by calling it — proj(X) — or with SequentialABC.transform(proj, X).

transform is deliberately not exported: in this package transform already names the config's prior→model-parameter map (cfg.transform, written transform(θ_raw) = … in the quickstart), so PCA's map stays qualified while the callable form proj(X) needs no name at all.

The components follow a canonical sign convention (the entry of largest absolute value in each component is positive), so a projection is reproducible and comparable across fits — plain eigenvector signs are arbitrary.

Fields: source, components (k × p), mean (length p), explained (fraction of total variance per component), name.

source
SequentialABC.summary_keys — Function
summary_keys(s::AbstractSummary) -> Vector{Symbol}

The keys s produces, in order. Declared by the summary itself, so it can be called before any simulation runs — that is what lets pca_reduce check a data matrix and namedtuple_to_vector fix the layout of a distance vector.

source
SequentialABC.compute_summary — Function
compute_summary(s::AbstractSummary, sim_output) -> NamedTuple

Apply s to a single simulator output and return a NamedTuple whose keys are exactly summary_keys(s).

Vector-valued input must be aggregated explicitly with aggregate: a Vector here is a legitimate single output (a time series, a field), so the replicate case is deliberately not inferred from the container type.

source
SequentialABC.compose — Function
compose(s1::AbstractSummary, s2::AbstractSummary; name = :composed) -> CompositeSummary

Chain two summaries into a CompositeSummary. Operands that are already composites are spliced, so compose(compose(a, b), c) and compose(a, compose(b, c)) both produce one three-part composite with the same key order.

sizes = compose(FunctionSummary(x -> x.n, :n), FunctionSummary(x -> x.m, :m))
summary_keys(sizes)      # [:n, :m]
source
Distributions.scale — Method
scale(s::AbstractSummary, scales::AbstractDict{Symbol,<:Real};
      name = Symbol(s.name, :_scaled)) -> ScaledSummary

Multiply selected keys of s by fixed factors:

summary_keys(scale(abm, Dict(:count => 1e-3)))    # unchanged; the values are scaled

Useful when one key would otherwise dominate a Euclidean distance because of its units. Factors are validated against s's keys at construction time.

This is a method of Distributions.scale — the scale parameter accessor for distributions, here meaning the rescaled summary — so using SequentialABC, Distributions resolves scale without qualification.

source
SequentialABC.pca_reduce — Function
pca_reduce(summary::AbstractSummary, X::AbstractMatrix{<:Real}, k::Int;
           center = true, name = :pca) -> PCAProjection

Fit a k-component PCA on X — one row per observation, one column per key of summary, in summary_keys(summary) order — and return the projection. The data has to come from somewhere: a pilot ensemble, a prior predictive run, or the observed data. A convenient source is the simulator itself — one raw output per prior draw, one summary vector per row:

rng = MersenneTwister(2026)
pilot = [sim.evolve(sim.model_builder(θ), rng) for θ in prior_draws]
X = reduce(vcat, permutedims.(namedtuple_to_vector.(compute_summary.(base, pilot))))
proj = pca_reduce(base, X, 3)

center = true subtracts the column means first. explained on the result reports the fraction of total variance each component captures, which is the diagnostic to check before shrinking a summary.

source
SequentialABC.transform — Function
transform(p::PCAProjection, X::AbstractMatrix{<:Real}) -> Matrix{Float64}

Project each row of X (one summary vector per row, in summary_keys(p.source) order) onto the fitted components: an n × k matrix of scores. X must have one column per source key.

Not exported — proj(X) is the short form and compute_summary(proj, output) is the per-output one (see PCAProjection for why transform stays qualified here).

proj(X)                          # n × k scores
SequentialABC.transform(proj, X) # the same map, by name
compute_summary(proj, output)    # the same map for one simulator output
source
SequentialABC.aggregate — Function
aggregate(reps::AbstractVector, summary::AbstractSummary;
          aggs = (mean = mean, sd = std)) -> NamedTuple

Apply summary to each element of reps — repeated simulator outputs of the same model, e.g. Vector of replicate runs — and aggregate every key. With the default aggs a key :count becomes :mean_count and :sd_count; the key order is aggregator-major (all means, then all standard deviations), matching the order of aggs.

aggs maps a name to any function of a vector, so aggregate(reps, s; aggs = (mean = mean,)) or (median = median, q90 = x -> quantile(x, 0.9)) both work. This is the summary-level counterpart of the samplers' own M replicate handling, which averages internally: use aggregate to build the observed summary from repeated measurements, or to summarise a pilot ensemble before pca_reduce.

s_obs_nt = aggregate(observed_runs, base)     # (mean_count = …, sd_count = …, …)
s_obs = namedtuple_to_vector(s_obs_nt)
source
SequentialABC.flatten_namedtuple — Function
flatten_namedtuple(nt::NamedTuple) -> NamedTuple

Flatten a NamedTuple whose values may themselves be NamedTuples into a single flat NamedTuple, joining nested keys with _:

flatten_namedtuple((a = 1, b = (x = 2, y = 3)))   # (a = 1, b_x = 2, b_y = 3)

Values that are not NamedTuples (scalars, arrays, …) pass through untouched. Duplicate keys after flattening throw an ArgumentError rather than silently dropping a value — this is what makes CompositeSummary safe when one of its parts returns a structured value.

source
SequentialABC.namedtuple_to_vector — Function
namedtuple_to_vector(nt::NamedTuple) -> Vector{Float64}

The values of nt as a Vector{Float64}, in key order — the bridge from a named summary to the numeric vector that a distance function consumes. Every value must be Real; anything else (an array, a string, a nested NamedTuple) raises an ArgumentError naming the offending key, because it has no single numeric value to compare against the observed summary.

source
SequentialABC.vector_to_namedtuple — Function
vector_to_namedtuple(v::AbstractVector, expected) -> NamedTuple

Rebuild a NamedTuple from a vector of values and a key order — the inverse of namedtuple_to_vector. Throws if the lengths disagree.

source
SequentialABC.validate_summary_keys — Function
validate_summary_keys(nt::NamedTuple, expected::AbstractVector{Symbol}) -> expected
validate_summary_keys(nt::NamedTuple, summary::AbstractSummary) -> expected

Throw an ArgumentError unless the keys of nt are exactly expected, in order; otherwise return expected. Used to check that a summary function returned what its declaration promises before the values are combined or projected.
